# Landlord chat-first page — plan (prototype, 2026-09-30)

An **alternative** landlord page, `/landlord-chat.html`, to show the team: the landlord works through
the chat instead of forms, sliders and tables. The existing `/landlord.html` stays as it is and keeps
working (its tests stay green). Both pages share the backend, the store and the signed-in landlord.

Branch `feature/landlord-chat-first` (from `origin/main` at `162c7ad`). Nothing is pushed and nothing is
posted on GitHub; the user decides in the morning.

## What the landlord sees

Desktop, three columns (phones stack them: slots, chat, Shortlist):

```
┌─────────────┬──────────────────────────┬────────────┐
│ Slot 1      │ chat turns (scroll)      │ Shortlist  │
│  avatar     │                          │ #3 A. Name │
│  name, rank │                          │   [×]      │
│  score      │                          │ #9 B. Name │
│  reason     │                          │   [×]      │
│  [Shortlist]│                          │            │
│  [Skip]     │                          │            │
│ Slot 2      ├──────────────────────────┤            │
│  …          │ > prompt          [Send] │            │
│ at a glance │ 💡 tip (rotates)         │            │
└─────────────┴──────────────────────────┴────────────┘
```

- **Sign-in**: the same landlord session as `/landlord.html` (`public/landlord/session.js`); the header
  has the language toggle (DE/EN), sign-out, and a small link to the classic dashboard.
- **Two Recommendation slots** (left): the two best-ranked applicants who are neither on the Shortlist,
  nor skipped, nor excluded by a Requirement. Each slot card shows:
  - an avatar;
  - the name;
  - the current rank ("#3 of 34") and the Match score;
  - the Recommendation reason (DE/EN, generated by code from the breakdown, as the dashboard's
    recommendation cards do);
  - three buttons:
    - **Add to Shortlist**: the applicant moves to the Shortlist sidebar, a short slide animation
      that is skipped under `prefers-reduced-motion`, and the next applicant fills the slot;
    - **Skip**: the next applicant takes the slot;
    - **Ask**: puts "Tell me more about A-007" (in the page language) into the prompt.
- **Skip is page state only**: forgotten on reload. A skipped applicant can come back when the ranking
  changes, but not while the ranking stays the same. When nobody is left, the slot says so (and that
  a reload brings the skipped ones back).
- **Avatars show the household shape only**, never gender: the pool records gender, but it is protected
  under the AGG. The shapes, as inline SVG in the page, with no image files:
  - `single`: 1 adult, no children;
  - `couple`: 2 adults, no children;
  - `family`: any children;
  - `group`: 3 or more adults, no children.
- **At a glance**, below the slots, compact: the pool stat tiles (`pool-overview.js` `statTiles`). A
  count that cannot be known yet (no rent → "can afford") shows "–" with its hint.
- **Shortlist sidebar** (right): each entry shows the small avatar, the name, its *current* rank (or
  "excluded: <reason>" when a Requirement now excludes it), the status label and a **remove** button.
  Status changes happen through the chat ("mark A-007 as invited").
- **Rank movement**: after a turn that changed the criteria or the flat details, the slots and the
  Shortlist show each rank's change since before the turn ("↑2", "↓1") until the next change. It is
  **optional**: build it last and drop it if time is short.
- **Chat** (centre): past turns above, the prompt at the bottom. It reuses `runLandlordTurn`
  (`public/landlord/chat.js`). After a turn whose events changed the criteria, the Shortlist or the
  flat details, the page refetches its data and redraws the slots, the tiles and the Shortlist.
- **Tips** (below the prompt, one at a time, rotating every ~8 s, like Claude Code's tips; clicking a
  tip's example puts it in the prompt):
  1. **Always first**: "Applicants are currently ranked mostly by {heaviest}; ask me 'give {example}
     30 % more importance' to adapt it to your liking."
     - {heaviest} is the criterion with the largest **active** share.
     - {example} is a different active criterion (the second largest).
     - Criterion names are the page's display labels (i18n), not the internal keys.
  2. **State-dependent**, shown only while they apply:
     - no asking rent: "Affordability isn't counted yet: tell me the asking rent (e.g. 'the rent is
       1,100 €') to judge whether applicants can afford it."
     - no size/rooms: "Tell me the flat's size and rooms (e.g. '65 m², 2 rooms') to filter out
       households too large for it (§ 7 WoAufG Bln)."
     - rent known but no Rent check: "Tell me the address with postal code to compare your rent with
       the Berlin Mietspiegel."
  3. **One per active criterion that is not the heaviest**: "Ask 'give {criterion} more/less
     importance'."
  4. **Requirements that are off**: "only clean SCHUFA", "no pets", "no smokers", "move-in by
     <date>", "rent at most a third of income", "complete documents only".
  5. **Always**:
     - "Ask 'why is A-007 above A-013?'";
     - "Ask 'tell me more about A-012'";
     - "Say 'mark A-007 as invited'";
     - "I remember your preferences across visits."

  Tip texts live in `public/i18n.js` (DE and EN). The tip list is a pure function of the page data (so
  it is unit-tested); the first tip is always first; the rest rotate in a stable order.

Hidden on this page (still working behind the scenes): the Listing form, the criteria sliders, the full
ranking table, the Excluded section, the profile panel.

## Decisions (the user's, 2026-09-30 — do not reopen)

1. **Rank before a Listing.** The page shows a ranking from the first visit. A fact about the flat that
   is still missing switches off what depends on it: while it is unknown, that part contributes
   nothing, and the rest are renormalised. Once the landlord gives it, it counts.
   - **Without an asking rent:**
     - affordability's share is 0 and the active criteria are renormalised to 100 %;
     - `rentToIncome` is `null`;
     - the `maxRentToIncome` Requirement is not evaluated;
     - `stats.canAfford` is `null`.
   - **Without the size or the rooms**, the `occupancyCompliant` Requirement is not evaluated.
   - **Without a Rent check** (it needs the address, size, rooms and rent), `canAffordAtMedian` and
     `medianRent` are `null`, as today.
   - **Changing an inactive criterion's weight still saves the weight.** When the landlord asks about
     affordability or occupancy while they are inactive, the chat does the change, says it will only
     count once the rent (or size and rooms) is known, and offers to take the rent, then the address
     and size, so it can also compare the rent with the Mietspiegel.
2. **Flat details through the chat**: a new chat Tool `update_flat_details` (below).
3. **Avatars**: household shape only (above).
4. **Layout**: slots beside the chat (above).
5. **Allowed overnight**: Playwright in the scratch directory (not in `package.json`), and a few live
   model turns with the user's `.env` (small cost). **Not allowed**:
   - pushing;
   - opening a PR or an issue;
   - any GitHub post.

## Decisions taken for the user (report them in the morning)

- **Relative weight changes are computed in code, never by the model** (ADR 0004 spirit): a new
  operation `adjustSelectionCriteria` and chat Tool `adjust_selection_criteria`.
  - **Input:** `changes: [{ criterion, factor } | { criterion, share }]`.
    - `factor`:
      - 1.3 for "30 % more";
      - 2 for "double";
      - 0.5 for "halve";
      - 0 for "ignore".
    - `share`: a target percentage, e.g. "make SCHUFA 40 %".
    - More than one change per call ("stable income matters most" → employment and affordability).
  - **Semantics:**
    - A changed criterion's new share = its saved share × factor (or the given share), in
      percentage points of the saved criteria.
    - The criteria not named keep their proportions and are scaled to fill the rest to 100 %.
    - Example: defaults, SCHUFA × 1.3 → SCHUFA 20 → 26 %; the other five (80 % together) are scaled
      to 74 %: affordability 30 → 27.75, documents/credibility/employment 15 → 13.875,
      previousLandlord 5 → 4.625.
  - **Limits (guards inside the operation):**
    - every share is between 0 % and **50 %**;
    - a request above 50 % is capped at 50 % and reported as capped;
    - at least two criteria must stay above 0 (a refusal otherwise, since one criterion alone
      would be 100 %);
    - when every criterion not named is at 0 and the named ones do not reach 100 %, it is a
      refusal telling the landlord to name what should fill the rest;
    - an unknown criterion is an input error;
    - validation completes before the store changes.
  - **Result:** `{ previous, criteria, applied: [{ criterion, from, requested, to, capped }], top }`,
    shares rounded to one decimal, so the chat can quote them and stay grounded.
  - **The absolute Tool loses weights.** The chat Tool `update_selection_criteria` keeps
    Requirements only: its `weights` field is removed from the chat Tool contract, so the model
    cannot bypass the limits. The HTTP `PUT criteria` (the classic page's sliders) is left as it is;
    note in the report that it has no 50 % cap, as a question for the team.
  - **Saved vs active shares.** The cap applies to the saved shares. Active shares (with
    affordability switched off) can exceed 50 %; the chat and tips quote saved shares and say
    "not counted yet" for an inactive criterion.
- **Flat details** are saved partially.
  - **Tool input:** `update_flat_details({ address?, livingAreaSqm?, rooms?, askingRent?,
    buildingYear? })` merges what is given into the landlord's saved flat details.
  - **Storage:** a new table/row beside `listings`; implementer's choice. When a full Listing already
    exists from the classic page, it seeds the flat details.
  - **The full Listing:** once the address, size, rooms and rent are all known, the Tool builds and
    saves the full Listing with its Rent check exactly as `PUT listing` does. The same
    `buildListing`, with the same validation messages, becomes the model's input error.
  - **Rent check failure:** when that fails (e.g. address not found), the partial details are still
    saved and the error is returned.
  - **Ranking input:** the ranking uses the flat details (plus the Listing's Rent check when there is
    one).
  - **The classic page**, when it saves a Listing, also updates the flat details, so both pages agree.
  - **Event:** the chat emits a new `flat` change event for this Tool.
- **Chat Tools rank without a Listing**:
  - `get_ranking`, `get_applicant_profile` and `update_selection_criteria` no longer refuse without
    a Listing;
  - their results say which criteria and Requirements are inactive and why:
    `inactive: [{ criterion | requirement, missing: ["askingRent"] }]`.
  - This changes the classic page's chat too: an improvement. Update its tests deliberately, not by
    deleting assertions.
- **API for the new page**: one new read endpoint `GET /api/v1/landlord/:id/overview`.
  - **Contents:**
    - flat details;
    - Rent check;
    - criteria with saved and active shares, and inactive items;
    - the **full** ranked list with name, household shape, rank, Match score and reason
      (`recommendationReasons` for every ranked applicant, not just the top two);
    - stats;
    - the Shortlist (as the dashboard's);
    - pool errors.
  - **The classic dashboard endpoint is unchanged**, so the classic page behaves as before. Document
    it in `docs/api.md`.
- **Prompt** (landlord system prompt; affects both pages' chat):
  - the flat details and the inactive items are in the context;
  - use `adjust_selection_criteria` for any weight change;
  - interpret vague requests ("matters more" ≈ × 1.3, "much more" ≈ × 1.5, "less" ≈ × 0.7) and say
    which criterion was chosen;
  - when a share was capped, say so;
  - save facts about the flat with `update_flat_details`;
  - ask only for what is missing and relevant.
- **Out of scope**:
  - ranking changes from free-text preferences that are not criteria;
  - profile photos;
  - skip persistence;
  - Shortlist status editing buttons;
  - issue #56 (address without postal code): the chat asks for the postal code;
  - issue #57.

**Changed during the build (2026-09-30).** A live probe showed the real model fills every optional
number with 0. It sent a `share` of 0 beside a `factor`, and a building year of 0, then an invented
1800. So every landlord Tool input now lists only what the landlord changes, with nothing optional:
- `adjust_selection_criteria` takes `changes: [{ criterion, by: "factor" | "share", value }]`;
- `update_selection_criteria` takes `changes: [{ requirement, value }]`;
- `update_flat_details` takes `facts: [{ fact, value }]`;
- `update_shortlist`'s `note` is required, and null keeps the note.

A guard test keeps optional properties out. See `docs/api.md`.

## How the work is split

The roles follow the user's multi-agent standard (from the BioNumbers project, without its testing
practices):

- **Orchestrator (the main session)**:
  - writes the briefs and settles each contract before any fan-out;
  - commits, and alone edits the shared files: `README.md`, `docs/api.md`, ADRs, `i18n.js`
    when it is shared by parallel writers, and this plan;
  - runs fault seeding and the final `npm test`.
- **Writers**:
  - implement against a settled contract;
  - in parallel, one file each;
  - never commit, never touch shared docs, never weaken a test (they stop and report);
  - end with a JSON report `{ changed_files, contract, notes, blocked }`.
- **Verifier**:
  - measures and never edits;
  - runs the suite, checks the diff against the claim, and names the test that would fail if a
    claim were false;
  - reports `{ green, suite, claim_holds, findings: [{ file, line, detail, wrong_if }],
    not_checked, blocked }`;
  - a separate writer applies its fixes.

## Round 2 (2026-09-30, the user's feedback on the first build)

The user's decisions:
1. **Tips change once per chat turn**, not on a timer. After a page load the first tip ("ranked mostly by …") shows; each finished turn advances to the next tip in the list.
2. **The Shortlist sidebar shows each entry's current rank only**: no ↑/↓.
3. **The slot's score line** reads "Match score 94.7 (↑1)", with the rank move in parentheses, green up or red down, as before. The rank ("#5 of 35") goes on its own line.
4. **The slots are not fully deterministic.**
   - The candidates are the top 6 applicants who are not hidden (shortlisted or skipped).
   - A freed slot gets a random pick from those 6 that is not already in the other slot.
   - An applicant keeps their slot while they stay in the top 6.
5. **Shortlist status again**, via an expander per entry: to invite, invited, declined. There's a note for "to invite" and "invited" only, saved with `PUT shortlist` as on the classic page.
6. **The landlord's subjective bonus: thumbs up and down** on the slots and on the Shortlist.
   - **Size:** additive bonus points, where ranking score = Match score + bonus. A thumbs-up adds N points and a thumbs-down subtracts N.
   - **N** is 5 by default and stays within 0–20 points. The chat changes it ("give my impression more weight") with `set_bonus_points`, computed in code and capped.
   - **The Match score itself stays objective**, and nobody's score or rank changes until the landlord rates someone.
   - **Clicking a thumb again reverts it.**
   - **Thumbs-up** colours green at once.
   - **Thumbs-down** colours red and replaces the card, like Skip: it stays hidden until the ranking next changes through the chat. The applicant can come back later, still showing the red thumb.
   - **AGG hint** beside the thumbs: "rate only what you could defend (reliability, communication, the viewing)". The chat refuses rating advice on protected grounds, and it cannot set ratings itself.

### Backend contract (settled before the fan-out)
- **Store:**
  - `setRating(landlordId, applicantId, rating)` with rating `1 | -1`;
  - `removeRating(landlordId, applicantId)`;
  - `getRatings(landlordId)` → `Map<applicantId, 1 | -1>`;
  - `getBonusPoints(landlordId)`, 5 by default;
  - `saveBonusPoints(landlordId, points)`.
- **Scorer:** `rankApplicants({ profiles, listing, criteria, ratings = new Map(), bonusPoints = 5 })`.
  - Ranked entries of *rated* applicants gain `rating` (1 | -1) and `bonus` (+N or −N). Unrated entries keep exactly today's shape, so every existing result and test is unchanged without ratings.
  - Order: matchScore + bonus, descending, ties by applicant id. `rank` follows that order, and so do the Recommendations.
  - `matchScore` is unchanged; stats are unchanged.
  - Every caller (dashboard, overview, chat Tools, applicant profile) passes the landlord's ratings and bonus points, so both pages agree.
- **HTTP:**
  - `PUT /api/v1/landlord/:id/ratings/:applicantId { rating: "up" | "down" }` → 200 `{ data: { applicantId, rating } }`. It returns 404 `applicant_not_found` or `landlord_not_found`, and 422 `validation_error`.
  - `DELETE /api/v1/landlord/:id/ratings/:applicantId` → 200 `{ data: { applicantId, rating: null } }`. It is idempotent and gives 404 for an unknown landlord or applicant.
- **Overview:**
  - top-level `bonusPoints`;
  - every ranked entry gains `rating: "up" | "down" | null` and `bonus` (number, 0 when unrated);
  - every Shortlist entry gains `rating`.
- **Chat Tool `set_bonus_points { by: "factor" | "points", value }`** (nothing optional):
  - It returns `{ previous, bonusPoints, requested, capped, maxBonusPoints: 20, top }` and emits `criteria`, since the ranking changes.
  - `get_ranking`, `get_applicant_profile`, `compare_applicants` and the context's top 5 carry the bonus, so answers about it are grounded. `compare_applicants` names the bonus as its own line and orders by Match score + bonus.
- **The model never sees names.** Ratings reach it only as ids with +N or −N.

### Frontend contract
- **`api.js`:**
  - `saveRating({ fetchImpl, landlordId, applicantId, rating: "up" | "down" })` → `{ rating } | { notFound } | { signedOut }`;
  - `removeRating({ fetchImpl, landlordId, applicantId })` → `{ rating: null } | { notFound } | { signedOut }`.
- **`board.js`:**
  - `fillSlots({ ranked, current, hidden, poolSize = 6, random = Math.random })`;
  - `slotCard(entry, { total, move })` → `{ applicantId, name, householdShape, scoreText, move: { text, label, direction } | null, rankText, reason, rating, bonusText }`;
  - `sidebarRows(shortlist)` → `{ applicantId, name, householdShape, placeText, excluded, status, statusText, note, noteAllowed, rating, removeLabel }`.
